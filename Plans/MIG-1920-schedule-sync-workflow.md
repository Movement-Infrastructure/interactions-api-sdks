# MIG-1920 — Schedule sync workflow and clean up dev triggers

[Linear ticket](https://linear.app/movementinfrastructure/issue/MIG-1920/schedule-sync-workflow-and-clean-up-dev-triggers)

## Background

Final cleanup of milestone 2 of the [Auto-generated SDKs plan](https://github.com/Movement-Infrastructure/minerva/blob/develop/Plans/AutoGeneratedSDKs.md). [MIG-1916](https://linear.app/movementinfrastructure/issue/MIG-1916/add-scheduled-sync-gha-that-opens-a-pr-when-the-spec-changes) built the sync workflow in four stages and shipped it with a temporary `push:` trigger so each stage could be iterated on from a feature branch — `workflow_dispatch` doesn't register until the workflow file is on the default branch. Stages 1-3 have now been exercised manually (sync PR #12 went end-to-end through MIG-1917's generation), so the dev trigger comes out and the real schedule goes in.

See `Plans/MIG-1916-scheduled-spec-sync.md` for the workflow's stage-by-stage design.

## Changes

- [x] `schedule: cron: '17 * * * *'` — hourly at :17. Off-the-hour minute per GitHub's guidance; cron workflows scheduled at the top of the hour contend with everyone else's and get delayed.
- [x] `workflow_dispatch:` for ad-hoc runs, with an optional `upstream_ref` input (branch/tag/SHA of `mig-readme-docs`). Takes precedence over `vars.READMEDOCS_SYNC_BRANCH`, which takes precedence over the upstream default branch. This is the "long-term shape" MIG-1916 stage 3.5 deferred to this ticket.
- [x] Removed the `push:` trigger (and its `branches-ignore: sync/**` guard, which only existed to stop the bot's own sync-branch push from recursing).
- [x] Renamed `.github/workflows/sync-spec-verify.yml` → `sync-spec.yml`. The `-verify` suffix was from stage 1, when the workflow only verified App auth.
- [x] Updated header comments to describe the scheduled behavior and idempotency guarantee instead of the PoC trigger; fixed the workflow filename in the generated PR body.
- [x] Added `concurrency: { group: sync-spec, cancel-in-progress: false }`. With push-only triggering, runs were effectively serialized by developer behavior; with cron + dispatch a manual run can land mid-schedule, and two concurrent runs could both see "no existing PR" for the same upstream SHA and race on the branch push.
- [x] README: named the workflow and its cadence in the pipeline overview, and added a "Running the sync by hand" section covering the dispatch input precedence and the re-run idempotency behavior.

## Verification

Everything below is post-merge: `schedule:` and `workflow_dispatch:` only register from the default branch, so this PR's own branch cannot exercise either. Corollary — removing `push:` means CI runs nothing for this PR beyond the YAML being well-formed. That is expected.

- [ ] After merge to `develop`, confirm the workflow appears under Actions with a **Run workflow** button (proves `workflow_dispatch` registered).
- [ ] Dispatch once with `upstream_ref` blank. Expect `changed=false` against the current committed spec, and `upstream_ref=(default branch)` in the Summary step.
- [ ] Dispatch once with `upstream_ref` set to a branch of `mig-readme-docs` that has a spec change. Expect a `sync/mercury-<short-sha>` branch, a PR against `develop`, and MIG-1917's generate workflow firing on it.
- [ ] **Idempotency:** with that PR still open, dispatch again against the same ref. Expect `skipped_existing=true` and no second PR.
- [ ] Observe at least 3 consecutive scheduled runs at :17 and confirm they're green no-ops (`changed=false`). Note the actual start times — GitHub's cron is best-effort and can drift by several minutes under load.

## Notes / follow-ups

- **Failure visibility** (carried over from MIG-1916): a scheduled run that fails is invisible unless someone checks the Actions tab. Now that the workflow is unattended this matters more than it did during the PoC. Worth a follow-up ticket for a Slack notification on failure.
- **Cadence**: hourly is a guess at the right latency/noise tradeoff. The spec changes rarely, so most runs are no-ops costing ~1 Actions minute each. If that's noisier than it's worth, dropping to every 6h costs little given `workflow_dispatch` is available for anyone who wants the sync now.
- `READMEDOCS_SYNC_BRANCH` should stay unset on the repo now that `upstream_ref` covers one-off testing. A variable left set would silently point every scheduled run at a stale branch.
