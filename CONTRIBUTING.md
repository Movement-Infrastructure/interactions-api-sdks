# Contributing

Every SDK here is generated by [`openapi-generator`](https://openapi-generator.tech/) from `openapi/v1/swagger.json`. Nothing under `sdks/` is hand-written, and edits there are overwritten on the next sync. Work out which layer your change belongs in first:

| Layer | Lives in | Change it when |
| --- | --- | --- |
| API contract | [`mig-readme-docs`](https://github.com/Movement-Infrastructure/mig-readme-docs) → `reference/mercury.json` | An endpoint, model, or field is wrong or missing |
| Generation | `templates/`, `sdks/*/openapi-generator-config.yaml`, `scripts/` | Output is wrong in a way the spec cannot fix |
| Automation | `.github/workflows/` | Sync, generation, testing, or publishing behavior |

A bug in the client surface is nearly always a contract bug. Fix it upstream and the corrected client arrives on the next sync.

## Layout

```
openapi/v1/swagger.json   # source of truth, synced from mig-readme-docs
sdks/                     # generated clients (only python is live)
templates/python/         # mustache overrides for generator defaults
scripts/                  # version bump, post-generation patches, gates
docs/                     # publish leak-audit checklist
.github/workflows/        # sync, generate, test, publish
```

## How the pipeline works

1. `sync-spec.yml` runs hourly at :17 and fetches `reference/mercury.json` from `mig-readme-docs`.
2. If it differs from the committed spec, the workflow opens a PR against `develop`.
3. CI regenerates each SDK, bumps the version from the PR's labels, and renders a changelog entry from a spec diff — all in one commit.
4. Sync PRs merge to `develop`, which publishes that version to TestPyPI as a staging release.
5. Promoting `develop` to `main` publishes the same version to PyPI. That promotion is the release.

Re-running the sync is safe: the branch name (`sync/mercury-<short-sha>`) derives from the upstream commit, so a run that finds an open PR for that SHA leaves it alone. Maintainers can also trigger a sync by hand and point it at an in-flight upstream branch.

## Versioning

Versions live in each SDK's `openapi-generator-config.yaml` as `packageVersion` and flow into the generated manifest. That field is the source of truth; nothing edits the manifest directly. `scripts/bump_version.py` rewrites it on every sync PR before the generator runs.

Apply at most one label:

| Label | Effect |
| --- | --- |
| `interactions-api-major` | Bumps major. Wins over the others. Needs a CODEOWNERS approval acknowledging the break, plus a migration note. |
| `interactions-api-patch` | Bumps patch. Bug fixes, docs, non-behavioral changes. |
| `interactions-api-minor` | Informational only — minor is the default. |

Tooling-only PRs need no label.

- **The bump is computed from the base branch.** Pushing again or toggling a label recomputes the same version rather than stacking a second bump.
- **Largest wins.** A PR carrying both major and patch is contradictory; the script honors the declared break.

A major bump emits an Actions `::notice::` so it shows in the run log. `--force-bump` overrides labels entirely, for out-of-band bumps.

`render_changelog.py` gates the two against each other: intended bump from labels, actual breaking changes from `oasdiff`. When they disagree, CI fails.

Dry-run without writing:

```bash
python scripts/bump_version.py \
  --current-config sdks/python/v1/openapi-generator-config.yaml \
  --labels-json '["interactions-api-patch"]'
```

## Generation helpers

All unit-tested under `scripts/tests/`:

- `bump_version.py` — computes `packageVersion` from PR labels.
- `patch_python_sdk.py` — fixes the generator has no config for, mostly `setup()` arguments. Exact-anchor patches fail loudly on a generator upgrade rather than silently dropping the fix.
- `render_changelog.py` — renders the `CHANGELOG.md` entry and gates label/spec agreement.
- `verify_readme.py` — checks the generated README before it becomes a registry page, since `setup.py` points `long_description` at it.

Template overrides live in `templates/<language>/`; anything absent falls back to the generator jar. `templates/python/README.mustache` documents why each override exists — read it before adding another.

## Running tests locally

Tooling tests need only Python:

```bash
pip install -r scripts/requirements-test.txt
pytest scripts/tests -q
```

SDK smoke tests import the generated package, so generate and install it first (Java 17 required for openapi-generator 7.10.0):

```bash
java -jar .cache/openapi-generator-cli.jar generate \
  -i openapi/v1/swagger.json -g python \
  -o sdks/python/v1 -c sdks/python/v1/openapi-generator-config.yaml

pip install ./sdks/python/v1
pip install -r sdks/python/v1/requirements-test.txt
pytest sdks/python/v1/tests -q
```

CI does this in `python-sdk-tests.yml` on every PR, as a required check. It carries no `paths:` filter on purpose — a path-filtered required check shows as perpetually pending on non-matching PRs and blocks merge forever.

## Adding a language

The placeholder directories under `sdks/` are the intended homes. Bringing one live means:

1. An `openapi-generator-config.yaml` under `sdks/<language>/v1/` with package name, project name, and starting version.
2. A `generate-<language>-sdk.yml` modeled on the Python one, including the bump and changelog steps.
3. A smoke suite and `<language>-sdk-tests.yml`, registered as a required check.
4. A publish workflow, registry-side trusted publisher setup, and a run of [`docs/publish-leak-audit-checklist.md`](docs/publish-leak-audit-checklist.md) against a real build artifact.

## Pull requests

Fill in [the template](.github/pull_request_template.md). If a generated SDK is involved, install it into a clean environment and smoke-test it before requesting review.

Maintainer procedures — credentials, key rotation, triggering the sync by hand, release promotion — are documented internally in the [DDx API Wiki](https://docs.superhuman.com/d/DDx-API-Wiki_d3Oex5wRfIO/Interactions-API-SDKs-setup-and-operation_sum1-dcU).
